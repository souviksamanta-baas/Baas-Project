Nexolia uses different authentication mechanisms depending on the endpoint type.

## Staff admin authentication (website)

Staff on `admin.nexolia.com.ar` use Supabase Auth **email/password** (Google OAuth deferred). Tokens are sent as `Authorization: Bearer <supabase-access-token>` to Nest `/admin/*`. The API rejects callers who are not in `nexolia_staff` (or holding a pending invite). Client OTP is **not** used for the staff portal. See [Admin API](/guides/admin-api).

## Owner API authentication

Owner-facing endpoints use Supabase Auth access tokens.

Send the token in the standard `Authorization` header:

```http
Authorization: Bearer <supabase-access-token>
```

Current owner-authenticated endpoints include:

- `POST /organizations/invites` — create a staff invite (owner bearer token)
- `POST /organizations/invites/accept` — accept invite after phone verification
- `GET /auth/identities/me` — verified login methods on the current session
- `POST /auth/identities/email|phone/request|verify` — bind missing email/phone (SMS for phone; see below)
- `POST /auth/identities/confirm-merge` — confirm absorbing another auth user’s negocios
- `POST /whatsapp/connection/register` — register merchant WhatsApp Cloud API number
- `POST /ai/drafts/{draftId}/approve`
- `POST /ai/drafts/{draftId}/reject`
- `POST /ai/copilot/query`

These endpoints validate the token server-side before allowing access to organization-scoped data.

## Linked identities (Actualizar perfil)

Email OTP and WhatsApp OTP historically minted **separate** `auth.users` rows (phone users use `{digits}@auth.nexolia.app`). QR staff invites attach membership to the **phone** user. Owners bind both methods on **Actualizar perfil** without switching session:

| Route | Auth | Purpose |
| --- | --- | --- |
| `GET /auth/identities/me` | Bearer JWT | `{ email, emailVerified, phone, phoneVerified }` |
| `POST /auth/identities/email/request` | Bearer JWT | Send link OTP (`purpose=link`) |
| `POST /auth/identities/email/verify` | Bearer JWT | Attach email **or** return merge preview |
| `POST /auth/identities/phone/request` | Bearer JWT | Send SMS link OTP (Supabase → Twilio) |
| `POST /auth/identities/phone/verify` | Bearer JWT | Attach phone **or** return merge preview |
| `POST /auth/identities/confirm-merge` | Bearer JWT | After Spanish confirmation, merge donor → current user |

Phone linking uses **SMS** (same Twilio path as login SMS), not platform WhatsApp. Deprecated `/auth/identities/whatsapp/*` aliases forward to the phone SMS routes.

Rules:

- **Not** `@Public()`. **Bearer header only** (no cookie session). Owner app only.
- Pure `nexolia_staff` callers with **no** tenant membership are rejected. Dual-hat staff who already own a negocio (same Supabase user as the Owner app) may link identities; absorbing a staff donor account is still blocked.
- Link OTP challenges use `auth_otp_challenges.purpose = 'link'`. A login OTP cannot bind an identity, and link verify **never** returns session tokens.
- Request OTP always returns `{ ok: true }` style success paths that do not enumerate whether the identity already exists as another account.
- If another `auth.users` owns the proven identity, verify returns `status: 'merge_required'` with org names/roles. The client must call `confirm-merge` after listing negocios that will be absorbed and warning that the other login **dejará de existir**.
- Merge keeps the **logged-in** user (`p_to` from JWT). `merge_auth_user` is **service_role only**; Nest derives ids from JWT + OTP — the app never sends user ids.
- After link/merge, a Spanish notice is sent on available channels (email and/or WhatsApp log path).
- Do **not** add `https://web.nexolia.com.ar` to CORS for this feature; marketing/`admin.nexolia.com.ar` must not call identity APIs.

Product copy and merge policy: [Vincular correo y teléfono (identidad del dueño)](https://souviksamanta.atlassian.net/wiki/spaces/BaaS/pages/45350913) (Confluence, under Nexolia).

## Public auth OTP endpoints

WhatsApp login OTP uses the Nexolia **platform WABA** (not merchant inbox numbers). These routes are unauthenticated and rate-limited at the edge in production:

- `POST /auth/otp/whatsapp/request` — send Meta authentication-template OTP (`purpose=login`)
- `POST /auth/otp/whatsapp/verify` — verify OTP and return Supabase session tokens / `tokenHash`
- `POST /auth/otp/email/request` | `verify` — same for email via Resend

The mobile client establishes the session from the returned tokens. Link OTPs (`/auth/identities/*`) reuse the same delivery path but **do not** mint a session.

**Production pilot:** owner login ships **email-only** (`EXPO_PUBLIC_AUTH_LOGIN_CHANNELS=email`). WhatsApp OTP remains implemented but disabled until Meta business verification and a Spanish AUTHENTICATION template are approved.

Optional SMS OTP still uses Supabase Auth → Twilio from the mobile client for staff invite-accept when enabled.

## Scheduler authentication

Operational maintenance jobs use a shared scheduler secret.

Send the secret in:

```http
x-baas-job-secret: <configured-secret>
```

Current scheduler endpoint:

```http
POST /tasks/run-maintenance
```

The API expects the value to match `BAAS_TASKS_JOB_SECRET`. Comparison is SHA-256 hashed then `timingSafeEqual` (avoids leaking secret length). If the secret is missing from the API environment, the endpoint returns `503 Service Unavailable`. The route is marked `@Public()` so it does not require a user JWT; the job secret is the only credential.

## Global JWT and organization membership

Authenticated owner routes require a valid Supabase access token. Nest registers these global guards:

1. `ThrottlerGuard`
2. `JwtAuthGuard` — `auth.getUser(token)` on every non-`@Public()` route
3. `OrgMembershipGuard` — when `organizationId` is present in params, query, or JSON body, the caller must be in `organization_members`

Skip flags:

| Decorator | Effect |
| --- | --- |
| `@Public()` | No JWT. Used for health, Meta webhooks, OAuth callbacks, public leads/OTP, and job-secret cron. |
| `@SkipOrgMembership()` | JWT still required. Used for `/admin/*` (Nexolia staff are not org members). |

Appointment invite email is **not** a generic mailer: `POST /appointments/invite-email` requires membership and loads title/times/notes from the stored appointment (`appointmentId` + `organizationId`). Clients must not send those fields.

Availability (`POST /appointments/assignee-availability`) requires membership, and every `userIds` entry must also be an org member.

Notification prefs/events are org-scoped the same way. Catalog and `run-scheduled` stay public; scheduled jobs still use the job secret.

## WhatsApp webhook signature

WhatsApp inbound webhooks use the Meta signature header:

```http
x-hub-signature-256: sha256=<signature>
```

When `WHATSAPP_APP_SECRET` is configured, the API validates the raw request body against this HMAC signature before processing the payload.

## Security guidance

- Do not expose service-role Supabase keys to clients.
- Do not send `x-baas-job-secret` from mobile or browser clients.
- Rotate scheduler and webhook secrets if they are accidentally exposed.
- Treat webhook signatures as required in production.
- `BAAS_OTP_PEPPER` and `BAAS_TOKEN_ENCRYPTION_KEY` are required when `NODE_ENV=production`.
- Do not expose `/mockups` in production (nexolia-web returns 404 unless `NEXOLIA_ENABLE_MOCKUPS=true`).
